# 《Ship your first Managed Agent》中文上手笔记

> 课程出处：Anthropic / Claude 在 **Code w/ Claude 2026** 开发者大会上的官方工作坊（Workshop），伦敦场主讲人 Isabella He（Anthropic 技术团队成员），时长约 37 分钟。主题是在 **Claude Managed Agents** 平台上，从零搭一个能 7×24 值守、自主排查线上事故的 SRE（值班）智能体。
>
> 配套仓库：`anthropics/cwc-workshops`，本笔记对应目录 `ship-your-first-managed-agent/`。

## 一、课程在讲什么（一句话理解）

不用自己写 Agent 循环（循环调度、工具执行、运行时、状态压缩都托管在 Anthropic 云端），你只需要把 **Agent、运行环境、会话、事件流** 这几个资源配好，Agent 就能在云端沙箱里自主读日志、跑命令、调用工具、开子智能体、写记忆、产出文件。

工作坊场景：一个虚构电商系统凌晨报警——库存变慢、结账变慢、购物车报错。页面上有一个 **离线的 SRE Agent** 面板，你的任务分四步把它一步步唤醒：单智能体 → 多智能体团队 → 记忆 → 事故复盘 PDF 输出。

## 三、环境准备

### 1. 前置条件

- Python **3.10+**
- [Claude Code](https://claude.com/claude-code)（工作坊方式：你只贴一句提示词，代码由 Claude Code 生成）
- 一个 **Anthropic API Key**（Managed Agents 默认对 API 账户开启，无需额外申请权限）
- 已锁定依赖版本：`anthropic==0.116.0`、`streamlit==1.46.1`、`plotly>=5.20.0`、`python-dotenv>=1.0.0`

### 2. 本地启动步骤

```bash
git clone <你的 fork 地址>
cd cwc-workshops/ship-your-first-managed-agent

python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate

pip install -r requirements.txt
cp .env.example .env               # 把 ANTHROPIC_API_KEY 填进 .env

python data/generate_log.py        # 生成 data/app.log（约 7.4 万行，不入库）
streamlit run app.py
```

仪表盘打开在 `localhost:8501`：Metrics（指标）、Logs（日志）、Deploys（部署）三个页面用模拟数据可以正常看；SRE Agent 面板显示 **"agent offline"**，这就是要你去补的部分。

### 3. `.env` 可选项

```bash
ANTHROPIC_API_KEY=sk-ant-...
# SRE_HANDLE=                       # 给本应用创建的云端资源加的名字标签，默认用户名+4位随机字符
# SRE_COMMANDER_MODEL=claude-opus-5-5   # 指挥者模型
# SRE_INVESTIGATOR_MODEL=claude-opus-5-5 # 调查员模型（可换 haiku 更快更便宜）
```

## 四、核心概念对照表

工作坊代码里的每个函数对应一个 Managed Agents 概念：

| 概念 | 含义 | 代码位置 |
|---|---|---|
| **Agent** | 智能体本体：模型、系统提示词、可用工具、技能（Skills）。配置变更会发布为同一 Agent 的新版本 | `setup_agent()` / `setup_investigator()` |
| **Environment** | 智能体容器的运行环境，云端沙箱；创建一次长期复用 | `setup_environment()` |
| **Session** | 一次正在运行的对话：Agent + 环境 + 挂载的资源 | `start_session()` |
| **Event（事件流）** | 先打开流，再发用户消息，然后逐条接收 Agent 的事件；工具调用结果回写进流 | `stream_reply()` |
| **Skill（技能）** | 一个文件夹（`SKILL.md` + 可选脚本），Agent 按需加载；文件夹改动会发布为新版本 | `setup_skill(folder)` |
| **Custom Tool（自定义工具）** | 云端 Agent 通过事件流回调你本机函数；本机返回字符串结果 | `handle_tool()` |
| **Multiagent（多智能体）** | 一个协调者（commander）带一份调查员名册（roster），每个调查员跑成一个独立线程（thread） | `setup_investigator()` + commander 名册 |
| **Memory Store（记忆库）** | 挂载进容器的持久化文件夹，分只读 / 读写两种 | `setup_memory()` |
| **Session Outputs（会话产物）** | Agent 写在 `/mnt/session/outputs/` 下的文件，经 Files API 列出并下载 | `download_outputs()` |

### 资源挂载路径（记住这几个路径，排坑用）

- 上传的日志：容器内 `/mnt/session/uploads/app.log`
- 记忆库：容器内 `/mnt/memory/` 下
- Agent 产出文件：容器内 `/mnt/session/outputs/`

## 五、四部分实操路线

> 仓库设计：`agent.py` 里的函数都是 `raise NotImplementedError` 的桩，`python check.py` 会驱动真实 API 逐个验收。工作坊的推荐方式是在第二个终端打开 Claude Code，每部分只贴一句提示词，由它填代码；每通过一部分再继续下一部分。
>
> 验收命令：
>
> ```bash
> python check.py              # 检查已实现的所有部分
> python check.py --part 1     # 只验收第 1 部分（1–4）
> python check.py --solution   # 跑 solutions/ 里的参考实现对照
> ```

### Part 1：单智能体上线（约 10 分钟）

**你要补的函数（8 个）**：环境、上传日志、技能、Agent、会话、事件流循环、本机工具处理器、删除会话。

**给 Claude Code 的提示词**（可口语化）：

```
get the agent online
```

**实现要点**：

1. `setup_environment()`：创建云端环境，配置 `{"type": "cloud", "networking": {"type": "unrestricted"}}`。
2. `upload_log()`：把 `data/app.log` 经 Files API 上传，拿到文件 ID。
3. `setup_skill(folder)`：上传技能文件夹；目录内容有变化时发一个新版本，返回 Agent 引用 `{"type": "custom", "skill_id": ..., "version": "latest"}`。
4. `setup_agent()`：组装模型、系统提示词、工具集、技能；配置没变就复用已存 ID，变了就更新成新版本。
5. `start_session()`：创建会话，把日志文件挂载进去（`mount_path: app.log`）。
6. `stream_reply()`：**先开事件流，再发用户消息**；遇到 `agent.custom_tool_use` 就调 `handle_tool()` 并把结果回写成 `user.custom_tool_result`；收到 `session.status_terminated`，或 `session.status_idle` 且停止原因不是 `requires_action` 时结束。
7. `handle_tool()`：四个本机工具——`list_incidents`（事故清单）、`get_metrics`（指标）、`get_recent_deploys`（近期部署）、`get_diff`（某次提交的 diff）；返回 JSON 字符串。
8. `delete_session()`：调用 API 删除会话。

**在仪表盘里验证**：刷新页面 → 新建会话 → 提问：

> What caused the checkout latency spike?

观察工具调用：`sandbox` 调用跑在云端容器，`local` 调用跑在你本机的 `handle_tool()` 里。

**可选调整**：

```
make the commander end every answer with a one-line status for an exec
```

### Part 2：多智能体团队（约 15 分钟）

**动机**：一个智能体一次只能盯一个页面；三个页面同时报警，需要一个团队。

**提示词**：

```
give it a team of investigators
```

**实现要点**：

- 新增 `setup_investigator()`：形状与 `setup_agent()` 相同，独立模型、独立系统提示词、独立工具与技能；子智能体只能用自己配置里的工具。
- 在 commander 的配置里加名册（`multiagent.coordinator.agents`），把调查员挂进去。
- 每个调查员在独立线程里跑，有自己的上下文和模型设置，**共享同一个容器**；子智能体的工具调用走同一条事件流，带上 `session_thread_id`，按同样方式答复即可。

**验证**：新建会话，说：

> Three pages are open. Run the incident.

指挥者会为每个页面开一个线程；调查员回报后，指挥者对比各根因。再开一个新会话重复同样问题——注意此时会话之间还互不通气，Part 3 解决记忆问题。

**可选调整**：

```
have each investigator rate its confidence from 1 to 5
```

### Part 3：记忆库（约 12 分钟）

**动机**：之前每个会话都从零开始；团队其实积累了知识——哪些服务共用数据库、哪些日志是噪音、上次事故怎么处理的。

**提示词**：

```
give it memory
```

**实现要点**（`setup_memory()`）：创建两个记忆库并挂载进会话：

| 记忆库 | 权限 | 内容 |
|---|---|---|
| 团队历史（team history） | 只读 | 从 `memory-seed/*.md` 播种：服务地图、已知噪音、复盘约定等 |
| 智能体笔记本（notebook） | 读写 | 初始为空；Agent 调查结束后自己写短笔记 |

**关键细节**：

- 记忆库在 **会话创建时挂载**，事后补挂不生效；要看到记忆生效必须新建会话。
- 挂载资源里的 `instructions` 是写给模型看的：只读库告诉它何时去查、要遵守什么约定；读写库要明确写"先查笔记，结论后存到 `/incidents/<日期>-<事故ID>.md`"——**不写明写入要求，Agent 就不会写**。

**验证**：重跑事故 → 打开 **Memory** 页面，笔记本里应有 Agent 写下的笔记，带版本历史（哪个会话写的）。再开新会话跑同样事故，指挥者会先翻自己的笔记：有时一分钟内直接作答，有时会让调查员回去复核笔记说法。

**可选调整**：

```
teach the team memory a new convention: every postmortem ends with a line on customer impact
```

### Part 4：产出事故复盘 PDF（约 10 分钟）

**提示词**：

```
let it write a postmortem PDF
```

**实现要点**：

- 给指挥者再挂一个技能 `postmortem-report`（`skills/postmortem-report/SKILL.md` 只规定复盘必须包含哪些要素和格式）。
- `download_outputs(session_id)`：通过 Files API 列出会话产物，下载符合 `wanted_output()` 过滤条件的文件，返回 `[(文件名, 字节), ...]`。
- Agent 在沙箱里自己写代码、自己画图（数据来自日志）生成 PDF；文件落在 `/mnt/session/outputs/`，回合结束几秒后出现在 Files API 列表里，聊天面板下方出现下载按钮。

**验证**：

> Write the postmortem PDF.

**可选调整**：

```
make the postmortem open with a one-page exec summary
```

> 改技能文件夹 = 发布技能新版本；改提示词文件 = 发布 Agent 新版本；改 `memory-seed/` = 重新播种记忆库。已在跑的旧会话保留启动时的版本，要看效果请新建会话。

## 八、多人共用一个 API Key 的注意事项

- 应用创建的每个资源都带你的句柄（handle）前缀，元数据里也打标签；资源 ID 存在 `.sre-state.json` 里复用，重启不会重复建资源。
- `python cleanup.py` 只删自己状态文件里记录的资源，建议先 `--dry-run` 看一遍。
- 共用 Key 依然是风险：持 Key 的人能读到、删掉它能触达的一切。办班场景建议用独立工作区建 Key、设消费上限、事后删除。
- 模型可分别配置：指挥者与调查员各用各的模型；调查员换成 `claude-haiku-5-5` 更快更省额度。

## 九、常见坑与排错

1. **面板一直 "agent offline"**：先确认 `.env` 里 Key 填好、依赖装齐、日志已用 `generate_log.py` 生成；再跑 `python check.py --part 1` 看具体哪个函数报错。
2. **事件流没有输出**：检查是否"先 `events.stream()` 打开流，再 `events.send()` 发消息"；顺序反了会漏掉打开之前发生的事件。
3. **子智能体工具调用无响应**：Part 2 之后，子智能体的工具请求也走同一条流，带上 `session_thread_id`；按普通工具调用同样回写结果即可。
4. **记忆不生效**：记忆库只在会话创建时挂载；改完记忆/提示词/技能后必须新建会话。
5. **找不到产出 PDF**：产物在回合结束后几秒才被索引；`download_outputs` 做几次轮询等待；确认文件写在 `/mnt/session/outputs/` 下。
6. **SDK 版本对不上**：桩注释里的调用形状基于 `anthropic==0.116.0`；若新版 SDK 签名不同，以官方文档为准，不要硬猜。
7. **不要改固定文件**：`provided.py`、`state.py`、`check.py`、`cleanup.py` 是固定的；自定义调整走 `prompts/`、`memory-seed/`、`skills/` 对应文件。
